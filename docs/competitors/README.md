# Vinkey 竞品分析

本目录收集 Vinkey 参考过或计划参考的开源项目、商业产品和 Agent 产品设计。目标不是做产品排名，也不是复述宣传页，而是回答三个工程问题：

1. 哪些用户流程已经被 Vinkey 采用，当前实现和原产品有何差异。
2. 哪些能力值得继续验证，进入哪个版本或业务链路前需要什么证据。
3. 哪些设计明确不采用，以及不采用的隐私、许可证、成本或领域原因。

## 统一口径

### 状态标签

| 标签 | 含义 | 进入产品的条件 |
| --- | --- | --- |
| `已参考` | 已转化为 Vinkey 的实现、数据模型或交互原则 | 以源码、测试或当前设计文档为准 |
| `部分参考` | 只采用其中一段流程，边界或实现方式不同 | 在对应业务链路验收中说明差异 |
| `待参考` | 有明确价值但尚未进入实现 | 必须补充用户场景、隐私边界和验收指标 |
| `观察` | 记录趋势或产品做法，尚无进入计划 | 不作为承诺，不据此增加依赖 |
| `不采用` | 已判断与 Vinkey 目标冲突或收益不足 | 记录原因，避免重复争论 |

### 分析边界

- 只记录公开可观察的产品行为、官方文档、公开仓库和公开许可证；不推测厂商隐藏推理或内部实现。
- 参考交互和架构思想，不复制 GPL/AGPL 项目的代码、提示词、资源或专有内容；许可证结论由发布前审查确认。
- 商业产品的能力可能随版本、地区、套餐和账号权限变化。报告必须标注观察日期，不把一次体验写成永久承诺。
- 每个结论都要落到 Vinkey 的业务对象：工作区、项目、会话、文档、上下文、任务、Artifact、Proposal、canon、记忆或模型连接。
- “参考”不等于“集成”。Vinkey 当前保持 `Tauri 2 + React + Rust + SQLite` 和 Ollama/OpenAI-compatible Provider 边界，不因竞品存在就引入其 SDK、账号体系或商用 API。

## 维护流程

新增或更新报告时：

1. 先在 [功能决策总表](FEATURE_DECISIONS.md) 增加功能行，分配稳定的 `CF-*` 编号。
2. 在对应竞品报告中记录来源、观察日期、证据强度和产品差异。
3. 明确写出 `已参考`、`待参考`、`观察` 或 `不采用`，不能只写“可借鉴”。
4. 若已进入实现，补充代码、测试或设计文档链接；若只是候选，补充验收问题和退出条件。
5. 同步 `docs/README.md` 和根目录 `README.md` 的入口；文档移动后执行链接检查。

## 评审原则

竞品的市场成熟度是进入正式名录的门槛，但不是 Vinkey 采用功能的理由。功能优先级仍按 Vinkey 的隐私、可解释性、文学创作闭环、本地模型可用性和实现成本判断。尤其要区分：

- **发现**：候选实体、关系、结构或检索结果，可以不准确。
- **建议**：模型生成的草稿、修改或规划，必须可审阅。
- **确认事实**：用户认可后才能进入 canon 或项目记忆。
- **正式写入**：必须经过范围锁定、源指纹检查和明确提交。
