# 竞品筛选方法论

- 版本：`2026-09-22`
- 适用范围：Vinkey 竞品目录中的开源项目、商业产品和 Agent 产品。
- 核心原则：进入“正式竞品列表”必须同时满足市场认可的充分条件；仅有设计启发价值的项目进入“设计来源/观察对象”，不与正式竞品混写。

## 1. 筛选目标

竞品筛选不是按 Star 数量做排行榜，也不是把所有相似项目都收进资料库。正式竞品必须能够证明：

1. 用户已经有足够时间真实使用它，而不是只看到一次发布或演示。
2. 项目/产品在最近一段时间持续维护，用户问题能够获得反馈或修复。
3. 存在跨来源的用户采用和反馈信号，说明它被真实使用并产生了市场认知。
4. 它与 Vinkey 的工作区、文档、创作、Agent、上下文、审核或本地隐私问题有明确可比性。
5. 证据可复查，结论不会依赖宣传文案或一次主观体验。

## 2. 市场认可的充分条件

以下条件为**合取条件**。候选对象缺少任一项，只能进入“设计来源”或“观察对象”，不能进入正式竞品列表。

### 2.1 存续时间

- 从首次公开可用、首个公开 Release、公开 Beta 或商业产品正式上线起，至评估截止日不少于 **90 个自然日**。
- 产品改名、仓库迁移或重新包装不能重置存续时间；必须追溯到最早可验证的公开记录。
- 仅有概念页、一次性 Demo、短期活动项目或没有可复查历史的私有产品不满足此条件。

### 2.2 持续维护

过去 180 个自然日内至少满足以下一项，并且没有超过 90 天的整体停滞：

- 开源项目：至少 2 次实质性 Release、功能变更、兼容性修复或安全修复；或有持续合并的高质量提交和 Issue 处理。
- 商业产品：至少 2 次公开版本更新、官方 Changelog、功能文档更新或明确的产品维护公告。
- 仅修改官网、重复发布营销内容、自动依赖升级或无用户可见影响的提交，不计为实质性维护。

### 2.3 用户反馈闭环

必须有至少两类相互独立的反馈证据，并能定位到具体产品：

- **产品内反馈**：GitHub Issue/Discussion、官方社区、支持论坛、应用商店评价或公开 Bug 追踪。
- **产品外反馈**：独立评测、技术文章、社区讨论、教程/插件生态、客户案例或可核验的第三方使用记录。

反馈不要求全部正面，但必须能看出用户在真实使用：有具体场景、问题、解决过程、版本或结果，而不是只有转发宣传。

### 2.4 市场认可信号

开源项目和商业产品使用不同的量化信号，但都必须至少满足一项强信号，并结合 2.3 的反馈闭环：

- **开源项目**：`GitHub Stars >= 1,000` 且 `Forks >= 100`；或有同等强度的包下载、发行版安装、活跃社区或企业采用证据。
- **商业产品**：有持续付费/订阅产品、公开客户或团队采用案例、稳定的社区规模、编辑器/应用商店分发，或多个独立渠道的长期用户讨论。
- 单独的 Star、媒体报道、Product Hunt 排名、一次爆款文章或厂商自报用户数都不能独立构成市场认可。

### 2.5 产品相关性

候选对象必须至少覆盖一个 Vinkey 的可比问题：

- 本地工作区、文档编辑或 Markdown 创作；
- 上下文检索、项目记忆、长文本分析；
- Agent CLI、Tool Loop、任务编排、审批或恢复；
- 多 Agent CLI 聚合、远程会话、模型路由或统一控制面；
- 人物/设定资产、写作协作、改稿审核或 Artifact 交付。

只有模型供应商、纯 API 代理、与 Vinkey 不可比的底层库，默认进入“生态参考”，不作为同层产品竞品。

### 2.6 风险与可复查性

- 项目不能已归档、明显停止维护或存在无法解释的来源断裂。
- 许可证、商业条款、凭据处理和数据外发边界必须可以查到；不清楚的部分标记为风险，不得包装成推荐。
- 每条证据记录 URL、采集日期、对应结论和证据等级；失效链接或过期版本必须在复审时处理。

## 3. 证据等级

| 等级 | 证据 | 可支持的结论 |
| --- | --- | --- |
| `A` | 官方仓库/Release/Changelog、官方文档、公开社区或公开支持记录 | 产品存在、功能行为、维护状态 |
| `B` | GitHub API 统计、应用商店/包下载、独立评测、客户案例、多个社区来源 | 采用规模、用户反馈和市场认可 |
| `C` | 单次演示、宣传文章、社交媒体转发、无日期截图 | 只能作为线索，不能单独入选 |

正式竞品条目至少需要：存续和维护各 1 条 `A` 级证据、反馈闭环 1 条 `A` + 1 条 `B` 级证据、市场认可 1 条 `B` 级证据，以及许可证/商业条款证据。

## 4. 评分与分层

评分用于在已经满足充分条件的对象之间排序，不用于替代硬门槛。

| 维度 | 分值 | 评估问题 |
| --- | ---: | --- |
| 领域相关性 | 0-5 | 是否直接涉及本地文档、文学创作或 Agent 工作流 |
| 维护可靠性 | 0-5 | 最近 180 天是否持续发布、修复和响应 |
| 用户反馈质量 | 0-5 | 是否能看到具体问题、用户场景和闭环 |
| 市场认可度 | 0-5 | 是否有跨来源的采用规模或商业使用信号 |
| 设计可迁移性 | 0-5 | 对 Vinkey 的业务对象和隐私边界是否有可复用价值 |

分层规则：

- `核心竞品`：通过全部硬门槛，且总分 `>= 20`，直接对应 Vinkey 的主要产品问题。
- `生态参考`：通过全部硬门槛，但主要提供 Runtime、CLI、路由、编辑器或平台能力，不与 Vinkey 完整产品同层比较。
- `设计来源`：有明确可复用设计，但未通过市场认可充分条件；不进入正式竞品排行。
- `观察对象`：证据尚未完整，保留线索并注明补证条件。
- `排除项`：不满足相关性、维护、风险或证据可复查性要求。

## 5. 评估流程

```text
候选收集
  -> 身份归一化（官方名称、仓库、产品/CLI/SDK 层级）
  -> 存续时间核验
  -> 180 天维护核验
  -> 产品内/产品外反馈核验
  -> 市场认可信号核验
  -> 相关性与风险检查
  -> 评分与分层
  -> 进入正式竞品名录或设计来源/观察名单
```

每个候选保留一份评估快照：

```yaml
selection_snapshot:
  candidate_id: string
  canonical_name: string
  category: core-competitor | ecosystem-reference | design-source | watchlist | excluded
  evaluated_at: 2026-09-22
  availability_started_at: string
  age_days: number
  maintenance_window_days: 180
  substantive_updates: number
  feedback_evidence:
    product_owned: string[]
    independent: string[]
  market_signal: string[]
  license_or_terms: string
  scores:
    relevance: number
    maintenance: number
    feedback: number
    recognition: number
    transferability: number
  evidence_urls: string[]
  decision: pass | fail | pending
  exclusion_reason: string | null
```

## 6. 复审与降级

- 每季度复审正式竞品；对于快速变化的 Agent 产品，每月检查维护和名称变化。
- 连续两个复审周期没有实质性维护，或用户反馈闭环消失，降级为 `观察对象`。
- 许可证、认证、数据外发或安全边界发生重大变化时，立即重新评估，不等待季度复审。
- 产品改名、仓库迁移、CLI 与 GUI 分拆时，先更新[术语规范](TERMINOLOGY.md)，再更新竞品名录和功能台账。

## 7. 当前筛选结论

本轮使用截止日 `2026-09-22` 的公开资料进行快照。正式名录见[竞品名录](COMPETITOR_CATALOG.md)。`Knote`、`StorySphere`、`graphify-novel` 等保留在原始调研中，但由于存续时间、采用规模或反馈证据不足，暂不称为正式竞品。
