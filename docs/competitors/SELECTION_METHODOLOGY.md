# 竞品筛选方法论

- 版本：2026-10-27，按“本地中文创作工作台”定位重整。
- 适用范围：产品竞品、专项/生态参考、观察对象与历史设计来源。
- 本版取消“用户指定即正式纳入”的例外。用户提供的名字或排名是研究线索；所有对象使用相同的证据规则。

## 1. 筛选目标与比较边界

Vinkey 的产品定位是**本地中文创作工作台**。收录需要回答：产品是否真实存在并被使用、当前能否作为有效参考、具体解决了哪个相同问题。不能把品牌知名度、代码仓库热度和某一项界面体验混为一个分数。

先识别产品与使用表面，再分类：

1. 中国区办公类 AI Agent：面向办公/文档目标持续推进任务，具有工具执行与成果交付的用户产品。
2. 本地文档与中文 AI 工作台：以文件、内容工作区、模型与创作交互为核心。
3. 中文通用助手与文档办公产品：覆盖中文阅读、写作、附件或文档编辑，但不默认具备完整 Agent 工作流。
4. 文学创作、知识与编辑器专项产品：解决领域资产、本地文档和编辑问题。
5. 开发者 Agent 与集成生态：主要作为执行机制、上下文或连接参考。

同品牌的聊天 App、办公 Agent、IDE、模型/API 和企业版分别登记。商业产品中文化不等于本地运行；开源不等于没有数据外发。

## 2. 统一收录条件

### 2.1 必备证据

正式竞品或正式专项参考须同时具备下列条件，缺项时进入观察，不由主观总分抵消：

| 条件 | 可接受证据 | 不充分的替代品 |
| --- | --- | --- |
| 可定位身份与产品范围 | 官方网站、文档、官方仓库、发行/分发入口；注明端别与版本 | 仅有中文品牌名、仿站、自媒体转述 |
| 真实采用 | 同类别独立市场统计；或可复查的商店/社区采用与具体使用反馈 | 厂商口号、一次演示、单篇宣传、用户指定 |
| 可核验维护与服务状态 | 版本历史、实质更新、问题修复或支持记录；核查归档、停服与迁移 | 单次官网更新、仅一个 pushed_at、没有日期的“持续更新” |
| 明确的场景相关性 | 能定位到文稿、工作区、任务过程、上下文、审核或交付中的具体问题 | 因为也使用大模型就视为同层竞品 |
| 结论可追溯 | URL、采集日、资料所属日、版本/渠道与限制 | 不带来源的综合评分和“市场公认” |

证据强度决定**能够写到哪一层结论**。独立统计可证明采用，不能证明默认折叠行为；更新日志可证明处理过某个问题，不能证明今天所有用户都已修复；商店评价是反馈入口，不自动证明反馈闭环。正式身份成立后，精确交互仍须单项补证。

### 2.2 存续、维护与成熟度

- 追溯首次公开可用与改名/迁移关系，仓库创建日不直接当作产品上线日。
- 默认查看最近 180 天，优先寻找至少两次可定位的实质更新或持续支持记录。只有提交时间和版本号时，只报告其可证明的活跃迹象，不宣称已审核提交质量。
- 90 天存续作为成熟度观察线，**不再作为所有产品的统一硬门槛**：新产品可以已有独立采用证据，成熟编辑器也可能发行周期较长。短期产品仍须满足全部必备证据，并明确稳定性与历史验证范围。
- 超过 90 天没有可见维护线索、长期没有公开发行、版本渠道断裂时触发复核；不能仅凭一次推送消除疑点，也不能仅凭发行间隔宣布停止维护。
- 已公布停服、迁移或产品定位变化时立即单列。历史市场地位不替代当前可用性。

这是对旧版机械时间门槛的统一修订，不是对某两个产品放宽条件。旧版未经逐项核验的“全部通过”与总分不继续沿用。

### 2.3 市场证据的使用

市场结论必须同时写明**机构、分类、地区、月份、指标与渠道**：

- 活跃用户、访问次数、下载量、评分数、付费人数和收入份额是不同指标。
- “典型产品榜单前二”不能自动扩展为完整市场份额前二；分母和跨端去重不明确时不计算份额。
- 同一报告的多家转载只算同一数据源。厂商转述独立报告，应尽量追到报告原文。
- GitHub Star/Fork 反映社区关注，不证明中国区占有率或产品质量；不再以固定 Star 阈值替代使用证据。
- 应用商店数据只覆盖对应地区/平台/应用。整套办公软件数据不能当作其 AI 功能采用，通用 App 数据不能借给同品牌新 Agent。
- 没找到数据只能写待核实，不能推断产品没有用户或不支持功能。

## 3. 证据类型：按来源角色记录

| 标识 | 来源 | 可支持内容 | 主要限制 |
| --- | --- | --- | --- |
| O | 官方产品文档、发行、状态公告 | 身份、声明能力、维护、商业/服务边界 | 官方描述不等于独立测量或全端实测 |
| M | 独立研究机构原报告 | 对应样本、时期和口径的采用/市场数据 | 不证明功能、体验或隐私行为 |
| P | 分发平台与仓库 API | 版本、评分数、仓库状态和社区规模 | 不等于用户数、市场份额或实质维护质量 |
| U | 用户实际观察、具体社区体验 | 对应场景、端别和版本中的行为与问题 | 不外推所有版本；必须区分观察与解释 |
| S | 新闻、第三方综述与转载 | 发现线索、交叉检查与补充背景 | 尽量追溯原始来源；转载不增加独立样本数 |
| D | Vinkey 设计判断 | 参考优先级、适配与独立设计结论 | 不写成竞品已有事实 |

“厂商域名上的用户文章”按作者与内容识别，不自动标为官方。证据类型不构成一个万能可信度排序；使用哪种证据取决于要证明的命题。

## 4. 身份、状态与参考优先级

| 登记身份 | 判定 | 使用方式 |
| --- | --- | --- |
| 正式竞品 | 必备证据齐备，与 Vinkey 有直接或相邻用户任务竞争 | 纳入同任务比较；具体能力另列验证状态 |
| 专项/生态参考 | 有身份、采用与维护证据，但只在领域设计或技术机制上可比 | 限定用途，不称同层中文创作产品 |
| 观察对象 | 缺官方身份、采用、维护或具体可比范围中的一项 | 明确缺口与升级条件；可以优先研究 |
| 维护复核 / 历史参考 | 以前有可比价值，但当前发行、维护或定位存在疑点 | 保留历史设计来源，暂停现役成熟度背书 |
| 退出跟踪 | 已确认停服计划、归档或产品退出 | 记录生效时间及迁移；不提前声称已经停服 |

研究优先级依设计问题决定：

- **界面与任务文案**：中国区同类办公 Agent → 中文文档/通用助手 → 海外及开发者产品的专项机制。
- **本地文稿与文件管理**：本地文档产品优先，核查中文编辑、保存与外发边界。
- **文学创作结构**：实际中文创作需求优先，同时保留专业写作工具的专项价值。
- **运行机制**：按机制适配与证据选择，避免将 shell、diff 等术语无条件移入创作者主流程。

同组若有同口径独立市场数据，可按该数据呈现并明确这是市场顺位；否则按参考场景组织，不编造综合排名。界面选择不能由市场顺位直接决定。

## 5. 调研与文档更新流程

1. 从类别收集候选，避免只围绕已有名字找支持材料。
2. 核验产品身份、端别与历史迁移。
3. 记录采用、维护、服务状态和相关任务，明确证据缺口。
4. 分别给出收录身份、当前状态和设计参考用途。
5. 在[正式名录](COMPETITOR_CATALOG.md)原位维护结论、必要量化数据、来源、核验日期与证据限制；历史版本及变更原因由 Git 提交记录管理，不新增按日期或版本拆分的快照型文档。
6. 同步术语、报告与功能决策；既有实现不因名录变动自动撤销，也不因新收录直接增加功能。

名录条目应包含以下信息；这是字段说明，不要求另建文件或逐产品复制 YAML：

```yaml
selection_record:
  canonical_name: string
  product_surface: string
  category: string
  evaluated_at: YYYY-MM-DD
  evidence:
    - kind: O | M | P | U | S
      url: string
      observed_at: YYYY-MM-DD
      source_date_or_period: string
      platform_version: string
      supports: string
      limitations: string
  inclusion: competitor | reference | watch | maintenance-review | retiring
  current_status: string
  vinkey_use: string
  unresolved: string[]
```

## 6. 复审与素材边界

快速变化的 Agent 每月检查名称、维护与服务变化；其余对象按季度复审。引用旧数据必须保留原月份，遇迁移、停服或证据失效原位更新，并在 Git 提交记录中说明变更原因。

仅保存必要的文字证据、链接、日期与独立设计结论。竞品截图、录屏、视觉资源及保留这些内容的衍生文件不得进入工作树或版本控制；判定按内容，不按路径或格式。用户提供素材在会话中观察，遵守 [AGENTS.md](../../AGENTS.md)。
