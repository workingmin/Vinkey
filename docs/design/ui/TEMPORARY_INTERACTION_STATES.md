# 临时交互状态设计

- 状态：逐事件过程记录、分页、保存恢复与折叠选择保持已实现；默认两层折叠已实现
- 日期：2026-10-26
- 修订范围：本次修正过程展示、历史查阅和折叠原则；第 2 至 4 节保留首版链路背景，不作为当前 Runtime 能力清单。当前实现差距见第 6 节。
- 关联文档：[对话页设计](UI_DESIGN_CHAT.md)、[状态、流程与验收](UI_DESIGN_STATES.md)、[Agent 与 Skill 建设计划](../agent/AGENT_SKILL_PLAN.md)

## 1. 目标与边界

临时交互状态用于表达任务此刻是否运行、正在做什么以及是否需要用户操作。临时状态与持久化过程记录必须区分：加载动画和当前状态提示在结束后清除，已经发生的响应、工具动作、分段推进、暂停、重试和结果记录保留，供历史查阅。

状态必须满足：

- 有真实的请求或任务阶段作为依据；没有对应 Runtime 事件时不显示“工具调用”等确定性文案。
- 右侧消息流、当前助手消息和输入区使用同一份状态，不各自维护副本。
- 状态结束后清除临时加载表现，不清除任务过程历史；错误、上下文超限和审批等待属于独立的终态/交互态，不伪装成加载中。
- 长耗时阶段显示可读的中文短标签，保留英文稳定标识用于日志、埋点和后续多语言。

## 2. 当前真实业务链路

当前 MVP 尚未实现完整的 Tool Registry、Skill Registry、IntentRouter 和 JobService；已先落地一个确定性的前置任务路由器和本地结构拆分路径。现有链路是：

```text
聊天输入
  → 本地 TaskRouter（意图/范围/是否需要模型）
  ├─ structure-segmentation → 本地结构解析 → 项目目录拆分文件 → SQLite 会话消息
  └─ 其他任务 → context budget → Tauri stream_chat
       → Rust run_stream → Ollama / OpenAI-compatible Provider
       → bytes stream → chunk / done / error → SQLite 会话消息
```

长文本入口目前由前端 `analyzeLongText` 编排：

```text
read_document
  → chunk_document
  → 复用或生成 `.vinkey/chunks/<cache-key>.json`
  → write_analysis_artifact(manifest)（`.vinkey/analysis/jobs/<job-id>/`）
  → 多次 stream_chat（局部摘要）
  → 多次 stream_chat（阶段汇总）
  → stream_chat（整体综合）
  → write_analysis_artifact
```

因此当前可以可靠表达 `sending`、`thinking`、`fetching`、`tool_calling`、`streaming` 和 `stopping`；不能把未来 Agent/Skill 的规划、审批、缓存或证据校验提前显示为已经发生。

## 3. 状态目录与实施决策

| 稳定标识 | 用户文案 | 当前是否增补 | 真实触发点 | 说明 |
| --- | --- | --- | --- | --- |
| `sending` | 发送中 | 现在实现 | 点击发送后、保存用户消息和建立请求期间 | 区分“已点击”和“模型已开始思考” |
| `thinking` | 思考中 | 已实现 | 请求建立后、首个模型 chunk 到达前 | 普通聊天的默认等待状态 |
| `fetching` | 读取资料 | 已实现 | 长文本切分、读取上下文和准备分析材料 | 不代表联网；联网检索需单独标注范围 |
| `tool_calling` | 执行分析 | 已实现 | 长文本 map/reduce/synthesis 阶段 | 当前实际是受控 Tauri command + 多次模型调用，不是 Tool Registry |
| `streaming` | 生成中 | 已实现 | 首个响应 chunk 到达后 | 对应草案中的 `typing`，内部保留 `streaming` 以贴合传输层 |
| `stopping` | 停止中 | 现在实现 | 用户点击停止，等待后端流结束 | 防止重复点击并明确取消尚未完成 |
| `context_too_large` | 正在精简上下文 | 暂缓 | 当前只做发送前预算校验 | 目前超限直接提示，尚无自动裁剪/压缩服务 |
| `retrying` | 重试中 | 暂缓 | 需要统一重试策略和幂等 request | 不能在一次失败后无依据地自动重试模型请求 |
| `stream_paused` | 输出暂时停顿 | 暂缓 | 需要流心跳、最后 chunk 时间和恢复协议 | 单纯等待 60 秒不能区分慢模型与断线 |
| `rate_limit` | 限流等待 | 暂缓 | Provider 返回 429 和 Retry-After | 当前错误映射未暴露该结构化信息 |
| `parsing` | 解析文档 | 目标态 | DocumentIngestion/OCR 事件 | 当前文本读取和分块是同步受控命令 |
| `routing` | 判断任务类型 | 部分实现 | 本地 TaskRouter；完整 IntentRouter 待 Agent Runtime | 当前仅覆盖确定性文档操作，歧义输入回退普通聊天 |
| `planning` | 制定执行步骤 | 目标态 | TaskPlanner / Agent | 应显示步骤数或当前步骤，不只显示转圈 |
| `awaiting_approval` | 等待确认 | 目标态 | Proposal / Approval checkpoint | 不是加载态，必须允许预览、接受或拒绝 |
| `checkpointing` | 保存进度 | 目标态 | JobService 持久化 TaskStep/Artifact | 需要可恢复任务模型 |
| `evidence_checking` | 核对来源 | 目标态 | EvidenceService | 分析报告生成后、提交前使用 |
| `generating_image` | 生成图片 | 暂不规划 | 尚无图像 Provider 或媒体任务 | 避免预先设计不存在的入口 |

`context_too_large`、`awaiting_approval` 和最终 `error` 不应与普通加载状态共用同一种视觉语义：它们需要行动入口或明确的终止原因。

## 4. 首版状态机

```text
idle
  → sending
  → thinking
      ├─→ fetching → tool_calling → streaming → idle
      ├─→ streaming → idle
      ├─→ stopping → idle
      └─→ error
```

约束：

1. `sending` 是短暂状态，用户消息保存失败时直接进入错误反馈，不继续显示思考中。
2. `thinking` 表示尚未收到首个响应；收到第一个 chunk 后只切换一次到 `streaming`。
3. 长文本分析的 `fetching` 对应切分和材料准备，`tool_calling` 对应 map/reduce/synthesis；阶段进度仍显示在输入区或任务详情中。
4. `stopping` 保留到 `stream_chat`/分析任务真正返回；不能点击一次就立即删除运行记录。
5. 当前运行结束后回到 `idle`；纯加载表现不进入历史，实际执行事件和终态仍须保留。

## 5. UI 表现

### 右侧消息流

- 当前助手消息作者名下显示状态短标签、呼吸点和可选进度；状态存在时助手气泡保留等待动画或流式光标。长文本分块提示应说明原文规模、估算 token、切分策略、单块预算、重叠范围和实际块数，并在消息区域内自动换行。
- 状态只属于右侧当前运行的助手消息，不改变左侧会话项的消息数、时间和布局。
- 用户切换会话后，后台运行仍更新原消息；返回原会话时恢复同一运行记录。
- `stopping` 使用警示色但不显示为错误；`awaiting_approval` 使用可操作的确认样式。

### 对话区和输入区

- 当前助手气泡上方保留状态行；空内容时显示打字动画，有内容后显示流式光标，不重复堆叠多个加载动画。
- 输入区提示与消息流使用同一状态源；运行期间发送按钮变为停止，`stopping` 时禁用并显示等待。
- 可恢复长任务的暂停、继续、取消和步骤重试位于输入区上方的紧凑控制行；它是当前会话的控制面，不重复充当消息正文。
- 状态文案使用 `aria-live="polite"`，避免每个 chunk 触发屏幕阅读器播报。

### 忠实展示实际任务过程（目标态）

优先忠实呈现 Agent 实际任务过程，再通过多层折叠按钮让用户自主选择阅读多少信息。过程本身具有执行观察和历史查阅价值，不能因文案相似或出现多次就视为无意义重复。本轮不设计过程记录的合并、压缩或聚合功能，也不以减少显示条数作为验收目标。

- 按实际发生顺序保留对外响应、工具/服务动作、阶段进展、分段结果及暂停、继续、失败、重试和完成记录；结果与产生它的过程保持可追溯关联。
- 同一用户请求内的多次 Agent 推进不等于多次用户提问；真实存在的推进边界应能识别。同一阶段再次执行、同名动作再次发生时仍保留各自记录，不能只留下最后一次。
- “继续处理任务过程”等提示可以在真实推进时多次出现，每次都应关联本次过程和状态。不能仅凭相同文案删除记录，也不能为了制造 Agent 感而虚构轮次、工具调用或进度。
- 过程与分段结果可按真实顺序交错出现，不要求全部过程集中在最终回答之前。若 Runtime 只提供完整最终结果，必须如实展示，不能把完成后的文本拆段渲染描述为多轮执行。
- 公开进展说明、动作和可展示的结果保留其业务含义；名称、时间、进度与真实事件对应。隐藏思维链、完整 Prompt 和未授权敏感信息不属于本方案要求采集的内容；这一边界不用于删去正常的公开过程说明。
- 完成、失败、取消、暂停与恢复状态以实际执行状态为准，不能仅因输出停止或活动记录不再更新就标记“已完成”。

### 两层折叠与阅读控制（已确认并实施）

- 默认采用两层：第一层为一次真实推进的处理过程，第二层为该次推进中的具体活动详情。任务状态栏始终可见，只提供“展开全部过程 / 收起全部过程”批量操作，不再增加最外层折叠容器。
- 推进边界来自执行器提供的 `segment.id / label / startedAt`；标签只用于展示，同名执行可有不同 ID。分组不合并事件；只有相邻且属于同一明确推进段的记录进入同一展示区，不能跨越其他记录重新排序。
- 未提供推进边界的旧记录使用“过程记录（未提供推进边界）”中性区域按原始顺序展示，不依据阶段名、文案或字数推测执行轮次。
- 活动详情承载动作信息、进度、耗时和只读产物入口。实际公开响应在所属过程后独立展示，不受两层折叠或过程分页影响；完整最终回答仍保留在消息正文。
- 当前默认：正在执行的任务展开推进段，打开历史任务时收起推进段，活动详情收起。任务完成不改变已有展开状态；批量操作只改变第一层，不重置第二层选择；后续新段沿用最近一次批量选择，已有手动选择保持不变。
- 折叠只改变可见范围，不删除、合并、覆盖或改写已有过程。收起后仍需有可发现的入口和真实状态提示，用户能够重新展开查阅。
- 用户已经作出的展开/收起选择优先；新事件、阶段切换和任务完成不得强制收起用户正在阅读的记录，也不得强制展开其已收起的内容。
- 上层收起后再展开，应保留此前下属内容的展开选择；跨会话或重启是否恢复展开偏好，另行讨论。过程历史本身的保留不以偏好持久化为前提。
- 用户查阅较早记录时，新内容不抢走焦点或强制滚动；需要时提供前往最新进展的入口。折叠按钮支持键盘操作，具有正确的 `aria-expanded`、`aria-controls` 和可访问名称。
- 修改提案、记忆候选和审批继续关联产生它们的执行过程与助手回合；折叠不能让待处理动作或失败状态变得不可发现。

### 历史查阅与性能

- 切换会话、重新打开历史会话或应用重启后，仍应能查阅已持久化的实际过程及其结果；暂停、失败和取消的任务同样保留历史。
- 保留任务、执行轮次/尝试、事件顺序、时间、状态和相关产物的关联；当前事件已增加可选 `segment` 元数据，后续统一 Runtime 协议仍需设计，不以展示层级替代真实执行关系。
- 长过程可使用分页、按需加载或虚拟列表控制内存与 DOM，但不能以“只展示最近 N 条”为由丢弃更早记录。尚未加载、历史缺失和记录不存在需要明确区分。
- 旧会话若只保存了部分过程，应说明历史记录不完整；不得从最终答案反推或补造缺失步骤。

## 6. 当前实现与目标差距

2026-10-26 已将默认结构落实为“真实推进段 / 具体活动详情”两层；全任务控制为批量操作，已交付响应位于折叠区域之外。

| 当前实现 | 边界与后续设计 |
| --- | --- |
| `appendWorkerActivity` 按 `jobId + sequence` 保留每个真实事件，允许乱序回放；只忽略同一事件的重复传输，不按阶段或文案合并 | Worker 在实际阶段入口、重试及恢复处创建推进段 ID；普通模型请求与上下文补充另起独立段；旧事件字段缺失时走未分段展示 |
| 前端取消最近 80 条限制，Rust Worker 取消最近 1,000 条截断；消息内每页渲染 50 条，提供上一页、下一页和查看最新记录 | 50 条是渲染分页大小，不是历史保留上限；目前仍全量读取历史，磁盘分页和大规模性能优化待后续处理 |
| 推进段与活动详情分别操作，批量按钮不增加折叠层；任务完成、上层收起和翻页不重置用户选择 | 当前挂载期间保持选择；跨会话/重启的展开偏好仍待讨论 |
| 执行中约每秒保存会话快照，结束时串行等待旧快照写完，再保存终态；没有正文的执行记录也保留 | 普通流式内容在突发退出时仍可能损失尚未写入的最后一个保存间隔；失败会提示，不声称零丢失 |
| 重开会话时读取关联 Worker 已持久化事件与完成产物；后台事件订阅刷新没有本地 ChatRun 的恢复任务 | 读取受工作区校验约束；旧版截断、序列缺口和读取失败会提示，不补造步骤 |
| 上下文补充前被替换的公开响应保存在过程记录中，并在两层折叠区域之外显示 | 仅保留实际公开响应；不采集隐藏思维链 |
| 长文本链路收到完整结果后直接展示，移除按空段制造“已生成第 N 段”的过程记录 | 尚未提供真实的结果小节流式交付，也不宣称实现了新的 Agent Loop |
| 消息 `runResult` 优先确定终态，历史失败事件不覆盖后续成功；暂停和停止状态明确展示 | 缺少可靠终态的历史显示待确认，不由无活动推断成功 |

验证：`npm test` 的 46 个文件、301 项测试通过，覆盖真实推进边界、同名推进独立控制、两层折叠选择保持、响应持续可见、事件保留与乱序回放、超过旧上限、保存串行顺序、会话恢复与后台订阅的作用域隔离；`npm run build` 通过。Playwright 浏览器检查使用 113 条记录，验证两层结构、键盘操作、批量控制、分页后展开选择保持，以及收起或翻页后阶段响应和最终正文仍可见，未出现页面错误。Rust 原生测试受当前 Linux 的 GLib 2.68.4（要求至少 2.70）及缺失 GTK/GDK 开发依赖限制，仍需在具备 Tauri 构建依赖的环境复验。

## 7. Service / Tool / Agent / Skill 映射

目标态统一由 Runtime 发出 `TaskEvent`，前端不根据猜测自行命名工具状态：

```text
TaskEvent {
  taskId, conversationId, requestId,
  phase, status, label,
  stepIndex, stepTotal,
  cancellable, resumable,
  startedAt, updatedAt
}
```

建议映射：

| 业务链路 | 状态 |
| --- | --- |
| IntentRouter 接收并解析入口 | `routing` |
| TaskPlanner 生成 TaskPlan | `planning` |
| DocumentIngestionService / `read_document` | `fetching` 或 `parsing` |
| StructureParserService / ChunkService / `chunk_document` | `tool_calling`，标签显示具体动作 |
| ContextBudgetService 超限处理 | `context_too_large` |
| ModelProvider 请求首 token 前 | `thinking` |
| ModelProvider 持续返回 token | `streaming` |
| ToolRegistry 执行搜索、文件读取或计算 | `tool_calling`，标签显示工具名 |
| ArtifactCacheService 命中/写入 | `checkpointing` 或短暂 `fetching` |
| Proposal 生成后等待用户 | `awaiting_approval` |
| EvidenceService 回溯来源 | `evidence_checking` |
| JobService 暂停、恢复、重试、取消 | `paused` / `retrying` / `stopping` |

上面的 `TaskEvent` 是状态映射示意，不是完整过程历史协议。目标态由实际 Runtime 事件派生当前状态，并保留独立的持久化过程记录；展示缓存可以只加载部分历史，但不能将“最近事件”作为唯一历史来源。事件身份、执行轮次/尝试、顺序和结果关联要求见[运行事件模板](../agent/AGENT_FLOW_TEMPLATES.md#6-运行事件模板)。

## 8. 不纳入临时状态的内容

- 模型不可用、响应解码失败、权限失败：统一错误态，提供重试或修复入口。
- 上下文超限但未开始请求：预算警告，不创建假的运行任务。
- 已完成的分析、草稿、Proposal 和报告：进入持久化结果或消息内容，不继续显示加载状态。
- 纯 UI 动画（按钮 hover、消息光标）：不写入 Runtime 状态。

## 9. 验收标准

- 发送、长文本分析、流式输出和停止操作均能在右侧消息流看到对应阶段，且状态不会残留。
- 切换会话后，后台任务状态和内容仍能更新；返回原会话不会丢失状态。
- 首个响应 chunk 到达前显示 `thinking`，到达后显示 `streaming`，不会同时显示两个主状态。
- 停止按钮在后端确认结束前显示 `stopping`，期间不可重复发送停止命令。
- 状态名称与运行日志的 requestId/taskId 可关联；错误不会被加载状态吞掉。
- 同一请求分多次推进时，每次真实推进均可独立查阅；相同文案、相同阶段的再次执行不覆盖之前记录。
- 公开过程、工具动作和分段结果按真实顺序关联；没有实际分段执行时，不制造轮次。
- 多层折叠只改变展示范围；用户手动选择在新事件、完成和上层收起再展开后仍有效，历史阅读位置不被新进展抢走。
- 两层按钮有正确的 `aria-expanded`/`aria-controls`，可通过键盘操作；任务级批量按钮不是第三层折叠。相同名称、不同推进段 ID 的过程可独立展开，结果在全部过程收起及翻页后仍可阅读。
- 超过 80 条过程记录的任务仍能查到早期记录；切换会话与重启后可回看已保存过程。旧数据缺失时明确提示，不补造。
- 暂停、继续、失败、重试、取消与完成显示真实状态；历史失败记录与最终执行状态分别可辨。
- 验收分离“当前实现回归”和“目标态待实现”；不得因已有折叠按钮就宣称完整历史和多层自主阅读已完成。
