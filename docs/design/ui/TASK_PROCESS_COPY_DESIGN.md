## 1. 设计范围与既定原则

### 1.1 沿用的设计

1. 相同文案可以多次出现。若对应不同执行、恢复或重试，它们具有各自的历史价值，不能因为看起来重复就删除或合并。
2. 第一层折叠控制真实推进段，第二层控制具体活动详情。任务状态常显；批量展开、收起按钮不构成第三层。
3. 用户决定展开多少信息；任务继续、完成和翻页不重置已有阅读选择。
4. 实际公开响应、阶段结果和最终回答保持可读，与产生它们的过程关联。
5. 不以文字长度、阶段名称或相同提示推测推进边界；旧记录没有边界时如实展示。

### 1.2 当前阶段交付范围

本方案完成**对话页内任务过程的界面与文案**，包括消息内状态、过程记录、输入区控制行、分析文件预览和结果关联。对话页原有导航、模型设置、正文编辑器和全局视觉体系继续遵循各自文档，本方案不将它们重做为一套新界面。

| 范围 | 当前阶段决定 |
| --- | --- |
| 可直接利用既有能力 | 中文命名统一、状态兜底修正、两层折叠、结果常显、50 条分页、历史与错误的区分、中文排版与可访问性 |
| 为准确显示必须补齐的依据 | 请求是否实际发出、暂停是否到达安全点、段是否结束、控制请求是否生效；未补齐时使用中性文案，不抢先宣称状态 |
| 不纳入本次实现计划 | 过程合并、第三层折叠、通用计划清单、运行中消息队列、任意任务并行、自动生成阶段小结、跨会话/重启持久化阅读偏好 |
| 延续既有权限 | 停止、恢复、文件读写、正文外发、修改提案审核与记忆确认沿用原业务授权；文案不扩大执行能力 |

任务记录与阅读偏好分开：实际过程必须按既有持久化机制保留；本阶段折叠选择只要求在当前消息组件挂载期间保持，重新打开会话采用第 4.6 节默认规则。竞品精确中文字符串仍待核实的条目，不妨碍 Vinkey 独立确定文案。

## 2. 多竞品对照与证据边界

### 2.1 比较范围与资料规则

Vinkey 定位为本地中文创作工作台，任务过程的界面与文案应优先比较中国区同类办公 Agent：WorkBuddy、百度搭子、千问办公。三者的收录来自同类采用与官方维护证据，见[正式竞品名录](../../competitors/COMPETITOR_CATALOG.md)；采用规模不直接证明某种措辞或折叠方式更好。

Claude Code、Cursor 用于补充任务控制和执行记录机制，Kimi Agent 模式、Kimi Work 分别比较复杂文档任务与交付。豆包通用助手与豆包工作分开登记；本轮尚未核实它们当前过程界面的精确措辞与折叠行为。正式身份、研究优先级和单项行为是否核验是三个独立问题。

资料核对日期为 2026-10-27。文档说明只能证明文档描述的行为，不能替代当前账号、版本、端别的实际体验。用户提供的 WorkBuddy 会话观察另行标注。本文不将英文官方说明的中文转述当作该产品真实的中文界面字符串。

### 2.3 各产品的观察与 Vinkey 取舍

**WorkBuddy：过程入口与后续推进。** 官方说明允许在同一任务中继续交流，并查阅中间步骤；用户观察补充了同名续接入口的真实价值。[S1](https://www.codebuddy.cn/docs/workbuddy/Conversation) 对 Vinkey 的启发是保留真实推进身份，动作说明与结果各自可读。继续推进不能自动等同于失败重试，重复出现也不构成合并理由。用户所见“深度思考”只作为该场景的原文观察，不直接成为 Vinkey 所有详情的名称。

**百度搭子：把操作对象说明白。** 官方 FAQ 明确将文件、脚本和浏览器操作纳入可查过程。[S3](https://cloud.baidu.com/discover/dumate-faq-guide-help.html) 因此，Vinkey 的活动文案应区分“读取文稿”“分析片段”“生成修改建议”，而不是统一写“执行分析”。多任务还要求状态具有明确归属；本次观察不据此提出新增并行执行能力。精确文案、右侧面板与折叠关系仍需用户实测，不能把第三方教程当作官方规范。

**千问办公：耗时活动与历史阅读状态。** 官方更新记录把长耗时工具执行、权限记录与历史阅读位置作为不同问题处理。[S11](https://docs.qwenwork.cn/release-notes/desktop) 对 Vinkey 的启发是：有工具执行时应显示真实活动；用户正在查阅历史时，不应因任务继续而丢失阅读位置。日志中的状态词仍需当前桌面界面核验，本轮不把它直接变成 Vinkey 的确定文案，也不据此改动两层折叠方案。

**Claude Code：计划清单与已发生记录分开。** 官方交互说明将待办清单、后台运行任务、详细记录查看区分开来。[S5](https://code.claude.com/docs/en/interactive-mode) Vinkey 可据此明确“准备做什么”与“已经发生什么”的语义。借鉴可查阅性，而非照搬终端命令、显示数量或聚合策略；本项目仍不合并真实事件。不同模型下清单可用性有条件，不能宣称每次执行必有计划列表。

**Cursor：明确控制操作影响的对象。** 官方文档指出检查点恢复作用于文件，对话记录仍保留；后台 Agent 则提供异步状态查看与后续交互。[S6](https://cursor.com/docs/agent/overview)、[S7](https://docs.cursor.com/background-agent) 对 Vinkey 的直接启发是把“继续处理”“重新执行步骤”“还原文稿”分开命名。“还原”不能用作暂停任务的恢复按钮，也不能由文件快照推断具有运行断点恢复能力。Vinkey 的修改建议仍按本产品审核规则处理。

**Kimi Agent 模式与 Kimi Work：任务目标和交付对象。** 官方概览描述从任务拆解到成果交付的流程；桌面产品介绍另强调持续目标和可介入过程。[S8](https://www.kimi.ai/zh-hans/help/agent/agent-overview)、[S9](https://www.kimi.com/resources/kimi-work-introduction) Vinkey 可把“生成回答”“生成修改建议”“汇总分析结果”与实际产出对应。计划完成不等于执行完成，生成完毕也不等于源文件已保存。两个交互表面分别比较，不照搬云端、并行或长时执行承诺。

**豆包：保留对照席位，精确体验待补。** 本轮没有足够官方过程说明或用户实测材料，不能给出其停止、继续、历史折叠的确定结论。[S10](https://www.doubao.com/) 第 11 节明确列出需要补充的瞬间；这些空白不影响已有证据支持的比较，也不应以常见聊天产品印象填充。

### 2.5 跨产品结论如何改变方案

以下是 Vinkey 的设计判断，不是各竞品共同使用了相同文字或层级的事实：

1. **“处理过程”是区域名称，“处理中”是任务状态。** 具体动作另行表达，避免所有层级都叫“思考中”。依据是 WorkBuddy 的多类信息与百度搭子的操作粒度，本方案选定“处理过程”作为推荐名称，待整体评审。
2. **计划、执行记录、结果分开定义。** Claude Code 与 Kimi 的流程材料支持这种语义区分；Vinkey 无真实计划时不生成虚构清单，也不因此新增第三层折叠。
3. **继续、重试、还原、追问分别命名。** Cursor 的对象边界与 WorkBuddy 的后续交互说明，提示“恢复”不能概括所有操作。
4. **“完成”必须带有明确对象。** 一次动作、一个段、一次任务、文件保存与用户审核是不同事实；用户可在任务完成后继续审核结果。
5. **两层折叠是 Vinkey 的既定选择。** 本轮资料不足以宣称竞品都采用两层。比较用于验证可读性与语义，不推导统一行业层级。
6. **独立设计与忠实记录同时成立。** 不复制竞品视觉资源，不删减真实过程；系统中文提示与实际文件名、公开响应各保留其含义。

## 3. 当前文案与实现问题

以下为 2026-10-27 工作区源码核对结果，不表示已经修复。

| 当前表现 | 对应实现 | 问题或边界 |
| --- | --- | --- |
| 固定标题“任务反馈” | [MessageActivity.tsx](../../../src/components/MessageActivity.tsx) | 容易被理解为用户评价或任务后的反馈，不能直接说明这里可以查阅过程 |
| 整体“正在处理”与具体动作并列 | 同上 | 通用状态本身合理；需要与具体动作分工，避免所有位置都只显示同一个泛化短语 |
| 空消息回退到“正在准备请求”或“准备请求” | 同上；[App.tsx](../../../src/App.tsx) 的流式回调 | 收到正文 chunk 后，`streaming` 记录仍可没有 `message`，此时可能错误回退到准备阶段 |
| 当前动作标题和说明取同一个消息 | MessageActivity 的 `execution-current` | 非 Worker 记录可能把同一个提示显示两遍；可以调整同一事件的排版，不删除活动历史 |
| 输入区“思考中”，过程区“正在准备请求” | App 的 `chatStatusMeta`；MessageActivity | `thinking` 覆盖准备和等待，不足以证明模型正在进行某种明确思考；两个位置的表述也不一致 |
| “运行中”“执行中”“正在处理”；“取消”与“停止” | [ConversationTaskControls.tsx](../../../src/components/ConversationTaskControls.tsx)、MessageActivity、App | 需要区分任务生命周期、历史事件和操作对象，再统一同义表述，不能全局替换 |
| “局部分析”“逐块分析”“最终综合”“全书综合” | [chatActivity.ts](../../../src/lib/chatActivity.ts)、任务控制组件、执行器 | 同一阶段有多套名称；“全书”对单篇、选段或多文档任务未必准确 |
| “Rust Map Worker”“manifest”“Pipeline” | [worker_service.rs](../../../src-tauri/src/worker_service.rs)、[longTextAnalysis.ts](../../../src/lib/longTextAnalysis.ts) | 实现术语进入用户主要阅读区域；适合保留在详情或日志，主文案描述动作与对象 |
| 段标题显示“最近记录：已完成”及耗时 | MessageActivity 根据最近事件及时间推算 | 最近一个活动完成不必然代表整个推进段完成；阶段完成事件与单项完成事件应进一步明确区分 |

本轮另核对到三项实现差距：`MessageActivity` 在没有活动记录时可能直接不渲染；当前活动失败可能直接影响运行中任务的总状态；`ConversationTaskControls` 使用一个跨任务动作锁，且暂停 API 在设置标志后即发布 paused。这些均需按第 7 节与真实生命周期/控制范围对齐，不能只替换中文字符串。

已有[临时交互状态设计](TEMPORARY_INTERACTION_STATES.md)第 2～4 节注明保留首版背景。本文以源码核对的现状为依据；不能把其中早期“目标态”直接理解为今天完全没有来源校验、重试等能力。

## 4. 必要的任务过程拆解

### 4.1 五类信息，两层折叠

这里的五类信息是语义分工，不是五层容器。

| 信息 | 用户的问题 | 展示位置 | 文案形式 |
| --- | --- | --- | --- |
| 任务状态 | 还在执行吗？结束了吗？ | 常显状态栏、任务控制处 | 处理中、已暂停、已完成、处理失败 |
| 真实推进段 | 这一次推进在做什么？ | 第一层折叠标题 | 阅读与分段、分析文本片段、汇总分析结果 |
| 当前动作 | 此刻具体在做什么？ | 当前进展行 | 正在读取《文稿.txt》… |
| 活动历史与详情 | 当时发生了什么，依据是什么？ | 第一层内活动列表；第二层展开详情 | 读取《文稿.txt》／当时状态；展开查进度、来源和结果 |
| 公开响应与交付结果 | 已经给出了什么？ | 对应过程之后，折叠外 | 实际响应、分析正文、修改建议、记忆候选 |

```text
处理过程 · 处理中                         常显状态
展开全部过程  收起全部过程                  批量操作
当前：正在分析第 3/15 个文本片段…           当前动作

▸ 阅读与分段                              第一层：真实推进段
▾ 分析文本片段                            第一层：真实推进段
    ▸ 读取《文稿.txt》                     第二层：活动详情
    ▾ 分析第 3 个文本片段
        原文位置、当时进度、可查看结果

已实际交付的响应或结果                     位于折叠外
```

上图说明位置关系，不表示“读取文件”一定发生在分析段，也不表示执行中一定已交付结果；实际归属和顺序服从事件。

### 4.2 推进段、业务阶段和结果小节的区别

“人物分析、叙事艺术、主题评价”可以是最终报告的小节，但不自动构成三个执行段。长文本执行器可能先分析多个片段，再统一综合这些主题；展示层不能从报告标题反推执行过程。

当前 `segment.id` 在实际阶段入口、部分重试和恢复处生成，表示已记录的执行边界；它不等于所有产品通用的 Agent 轮次。同一个业务阶段可以分成多个推进段，同一个推进段也可以包含多个活动。不得把重试后的段计数宣传为模型完成了更多业务步骤。

首段使用具体动作名称；真实继续执行有三种不同语义：

| 情形 | 标题或动作 | 记录要求 |
| --- | --- | --- |
| 暂停后恢复同一任务 | “继续分析文本片段”；动作“已继续处理” | 有恢复事件；保留暂停前记录与新的段身份 |
| 补充资料后再次请求模型 | “补充资料后继续回答” | 有真实补充和再次调用；原有公开响应保持可见 |
| 失败后再次尝试 | “重新分析文本片段”；动作“开始第 2 次尝试” | 有失败与重试事件；不能混写为普通继续或掩盖失败 |

若只知道存在新的推进边界，不知道具体动作，才使用“继续处理”作为后续段兜底。现在仅有 `id / label / startedAt` 时，不应从相同标签推断上述原因；需要执行器提供原因或明确的段标签。

### 4.3 按实际任务选择过程路径

| 任务类型 | 实际路径与文案 | 能力边界 |
| --- | --- | --- |
| 普通对话、构思、续写 | 准备任务 → 发起模型请求 → 生成回答 → 交付 | 发起请求前不能显示“等待模型响应”；首个 chunk 后不能仍显示准备 |
| 文本分析 | 阅读与分段 → 分析文本片段 → 按需汇总 → 综合分析 → 核对引用 → 交付 | 章节、分卷、汇总层级可能不存在；来源校验依执行路径支持情况展示 |
| 补充上下文后回答 | 原有响应 → 补充文档概况 → 再次生成回答 | 当前补充可能只含结构与元数据，不能宣称重新阅读全文 |
| 本地章节拆分 | 解析文档结构 → 写入拆分文件 → 展示文件清单 | 不必经过模型；不得显示“深度思考”或“模型正在拆分” |
| 项目结构概览 | 整理项目结构 → 展示概览 | 若只使用目录和已有结构信息，不能称为“已分析项目全部正文” |
| 修改文稿 | 读取授权范围 → 生成修改建议 → 展示待审核提案 | 建议生成完毕不代表已经修改或保存源文件 |
| 记忆候选 | 整理候选 → 等待用户确认 → 按实际操作反馈 | 回答完成与候选待确认可并存；不让候选等待把整个回答伪装为仍在生成 |

这些是语义路径，部分中间动作当前还没有独立事件。后续实现应在实际动作边界记录事件；本次不要求为了填满路径而补造记录或固定数量的步骤。

### 4.4 计划、执行、阻塞与交付

一次任务的用户可见状态按下列事实拆解。它们是解释文案所需的状态，不要求改动全部内部枚举，更不要求每次任务都走遍所有状态。

```text
收到任务 → 准备材料 → 实际执行 → 交付结果 → 结束
                        │
                        ├─ 需要用户补充 → 等待答复 → 继续执行
                        ├─ 暂停生效 → 等待用户继续 → 新推进段
                        ├─ 调用失败 → 已安排重试 → 新尝试
                        └─ 停止请求 → 等待退出 → 已停止

可选的“处理计划”说明未来准备做什么，不提前生成已执行活动。
实际结束后，结果仍可能待审核、待应用或待保存。
```

| 区分项 | 用户可见表达 | 记录与控制要求 |
| --- | --- | --- |
| 计划已生成，尚未执行 | “处理计划：先分析片段，再汇总结论” | 只有存在真实计划对象或公开计划说明才展示；未执行项不带完成勾选 |
| 实际动作开始／结束 | “开始读取…”／“读取完成” | 用真实事件记录，不从计划清单推断已执行；失败也单独保留 |
| 必要信息缺失，任务被阻塞 | “需要你补充分析范围” | 展示可回答的问题；与非阻塞的阶段说明分开，不继续显示普通加载动画 |
| 人工审批阻塞下一步 | “等待确认后继续” | 说明将执行的动作；既有权限规则不因文案变化增减 |
| 后台仍在执行 | “正在后台处理” | 仅在执行器确实继续运行时使用；不承诺关闭应用后一定继续 |
| 用户补充需求 | “已收到补充要求” | 仅表示收到；是否排队、立即采纳或重启须有实际实现；本轮不新增消息队列 |
| 任务停止后仍有部分成果 | “已停止”；附实际已保留结果 | 不把部分结果叫完整报告，不因停止而删除历史 |
| 文件还原与任务恢复 | “还原文稿”／“继续处理” | 是不同控制对象；前者不清除过程，后者不宣称已撤销文件改动 |

“处理计划”若后续实现，可作为对应推进段内的公开说明或独立响应展示，不加最外层折叠。对简单任务，不额外制造规划步骤；对固定工作流，也不得把程序内预设顺序说成模型刚完成的自主规划。

### 4.5 页面布局与信息分工

过程附着于产生它的助手回合；一次任务多次推进保留在同一任务内。过程区总标题、当前状态和需处理事项始终可见，不再增加包住全部内容的折叠容器。文稿正文、公开响应与已交付产物保持正常正文对比度。

```text
助手回合                                      消息时间 / 复制回答
处理过程 · 处理中 · 26条记录                   不可折叠
当前：正在分析第 3/15 个文本片段…               当前实际动作
展开全部过程    收起全部过程                   只操作第一层

▸ 阅读与分段                  4条记录 · 14:02:01
▾ 分析文本片段               22条记录 · 14:02:03
  ▸ 5. 开始分析第 1 个片段     当时状态：执行中
  ▸ 6. 第 1 个片段分析完成     当时已完成：1/15
  ▾ 7. 开始分析第 2 个片段
       来源：《文稿.txt》 · 实际原文位置
       当时已完成：1/15 个片段
       查看分析文件                         有真实文件才出现

已实际交付的公开响应                           两层折叠之外
▸ 继续分析文本片段             有真实续接才出现
已实际交付的后续响应                           按发生顺序展示

上一页   第1–50条 / 共86条   下一页   查看最新记录

——消息流底部——
《文稿.txt》分析 · 处理中       暂停任务   停止任务
[引用文件] [输入框：可编辑草稿] [当前模型] [上下文] [停止]
```

上图展示组件位置，不是一条保证出现的执行路线。分页控件放在过程记录列表尾部；公开响应不参加分页、不因换页重复复制。多个公开响应沿事件顺序保留；属于同一真实段但被公开响应分隔的过程片段可以有多个展示入口，仍共享真实段身份，不能把展示片段数称为执行轮数。

| 区域 | 显示内容 | 行为与空间约束 |
| --- | --- | --- |
| 消息内状态行 | “处理过程”、任务状态、真实记录数；已结束且时间可信时附总历时 | 不放原始任务 ID、内部枚举或目录；任务目标沿用用户消息/已有结构化任务摘要，普通消息不重复抄整段问题 |
| 当前动作行 | 一条当前动作，或阻塞/控制过渡说明 | 无额外信息时不重复标题；结束后移除进行时动作，结果与历史留下；无记录但已有真实运行时仍显示状态 |
| 第一层 | 真实段名称、记录数、开始时间；明确段终态才附状态/历时 | 整行按钮只负责折叠；不能把文件链接、停止按钮嵌套进该按钮 |
| 第二层 | 活动标题、当时状态、时间；展开后显示范围、进度、结果/错误和已有诊断信息 | 技术字段放在同一详情内的静态小节，不增加第三层；无详情时显示普通记录行，不提供空展开按钮 |
| 阻塞/失败提示 | 具体原因、影响范围、可执行的下一步 | 位于折叠外并关联对应任务；历史失败只在原活动保留，不持续冒充当前错误 |
| 结果与文件 | 实际公开响应、最终正文、修改建议/记忆候选入口 | 折叠与分页不遮蔽；“生成”“应用”“保存”分开反馈 |
| 输入区上方控制行 | 当前会话中具有控制能力的任务标题、状态与按钮 | 始终明确控制哪项任务。状态来自同一视图数据，不显示另一会话任务；多项恢复任务按行分列，不因此新增并行执行入口 |
| 输入框停止按钮 | 停止当前前台执行 | 无对应前台执行时恢复发送；后台任务用所属控制行操作，不将“发送”误变成停止其他任务 |

运行中可编辑下一条草稿；本阶段不接受运行中追加消息队列，发送行为沿用单次执行限制。只有真正进入输入/确认阻塞时才显示相应专用答复或审批入口，普通草稿不自动作为恢复指令。

### 4.6 两层折叠、分页与阅读位置

| 情况 | 第一层推进段 | 第二层活动详情 | 结果与阅读位置 |
| --- | --- | --- | --- |
| 新任务执行中首次显示 | 默认展开 | 默认收起 | 实际正文正常出现，不生成占位分析结论 |
| 历史任务首次打开，已结束或暂停 | 默认收起 | 默认收起 | 结果和当前阻塞/错误可见 |
| 返回仍在执行的任务，组件已重新挂载 | 默认展开 | 默认收起 | 当前阶段不承诺恢复上次折叠偏好；任务事实仍从保存记录恢复 |
| 点击单个段或活动 | 仅改变目标项 | 上层收起不清空下属选择 | 保持焦点于触发按钮 |
| 展开/收起全部过程 | 批量覆盖已有第一层选择，并设置之后新段的默认值 | 保留所有活动详情选择 | 不折叠正文，不改变当前页 |
| 用户在批量操作后单独改一段 | 该段手动值优先；其他段沿用批量值 | 不变 | 下一次批量操作可再次覆盖第一层手动值 |
| 新事件、同名新段、任务结束 | 不改已有选择；新段继承当前默认值 | 新活动默认收起，旧活动不变 | 不因任务完成强制收起或滚动 |
| 翻页后返回 | 选择按稳定展示身份恢复（真实段 ID 加分隔事件 ID），不按行号错配 | 详情选择仍保留 | 50 条/页仅控制渲染，不截断保存历史 |

在列表尾部且未主动离开时，可以跟随当前页新增内容；用户向上滚动、选择文字、展开历史或翻页后停止自动跟随。新增内容不抢焦点。新记录落到后续页时不自动翻页，提供“有新记录 · 查看最新记录”；点击后转到最新页并滚至最新活动，但尊重用户已收起的段，不强制展开。看完历史回到底部可恢复跟随。前端执行这些行为前需补齐滚动位置检测，不能把现有分页按钮当作已完成自动跟随。

计数显示全部已加载的真实记录；无法获得总数时写“已加载 {N} 条记录”，不写“共 {N} 条”。已知缺口、读取失败、确实没有记录分别提示。较大历史本阶段仍沿用全量读取，磁盘分页和虚拟列表以后另行设计，不能以性能为由删除早期事件。

### 4.7 视觉、窄栏与可访问性

复用现有颜色、字体与间距 token。结果正文为视觉主层，过程标题为次层，时间与技术信息为辅助层；可查过程不使用低到难以辨认的灰色，也不通过隐藏历史减少信息。

- 标题和动作采用 13–14px 正文字级，辅助信息不小于 12px；正文沿用消息样式。段间距 8–12px，活动行上下留 6–8px；长标题换行，不用固定高度裁断内容。
- 第一层保留清楚的折叠箭头，第二层缩进一个层级，使用细竖线辅助归属；不按每一条事件堆叠大卡片。可点击区至少 32px 高，独立图标按钮至少 32×32px。
- 以状态文字配合图标表达处理中、暂停、失败和完成，不能只用颜色区分。只有当前确在推进的项显示轻量动效；暂停、待答复、状态未知和终态停止加载动画。尊重系统减少动态效果设置。
- 以**对话栏可用宽度**适配：宽度不足 480px 时状态和批量按钮分行，活动时间移到次行，控制按钮换行。360px 宽度和 200% 缩放下仍能操作，不造成整个对话区横向滚动；单独的长代码/表格允许局部滚动。
- 文件名在摘要中可视觉截断，但保留扩展名并能在详情查看完整名称/相对路径；任务状态、失败原因和按钮不能只靠悬停提示读取。
- 折叠按钮支持 Tab、Enter/Space，正确设置 `aria-expanded`/`aria-controls`；同名段的可访问名称加入开始时间或展示序号以便区分（序号不命名为执行轮数）。无详情行不进入无意义的按钮焦点序列。
- 当前任务用一个 `aria-live="polite"` 状态区播报关键状态变化，输入区不重复播报同一变化；不随 token 或每秒计时重复读屏。需操作的错误可用 `role="alert"`；历史错误不在每次展开时重复警报。
- 文件预览复用现有只读对话框，焦点限制在对话框内，Esc/关闭后回到打开按钮。它是产物操作，不是过程第三层折叠。

### 4.8 本地文件、失败与部分结果

每条提示只描述已经验证的范围。“读取文档概况”与“读取正文”，“分析选段”与“分析全文”，“核对引用”与“证实结论”分别命名。未完成的分析可保留真实部分输出，并标为“部分结果”；中间文件存在不代表完整报告生成成功。

“查看分析文件”沿用只读预览能力，面向用户显示实际文件名、用途和保存位置；内部目录、缓存键与任务 ID 放在相关详情或预览信息中。当前解析为清单 JSON 时称“分析文件清单”，不能承诺已经提供可打开任意文件的浏览器。清单不存在、文件失效和读取失败各有提示，不清空已经显示的回答。

任务完成但会话记录保存失败时同时显示“已完成”与“过程记录保存失败，重新打开后可能不完整”，不能伪装为分析失败，也不能承诺历史已经完整持久化。文件输出失败需说明失败的文件；若文件是任务必须交付物，任务按执行器结果标为失败，已有正文作为部分结果保留。正文生成任务成功后，用户另行保存文稿失败只影响保存操作，不回写原任务终态。

## 5. 文案目录

本节为本方案推荐使用的规范文案，待整体评审；不是多套并列选项。编号用于评审、实现映射和验收，不要求直接成为代码键名。

### 5.1 常显状态与阅读入口

| 编号 | 场景 | 当前文案 | 设计文案 | 触发和限制 |
| --- | --- | --- | --- | --- |
| CP-01 | 过程区总标题 | 任务反馈 | **处理过程** | 固定区域名，始终显示，不作为第三层折叠按钮 |
| CP-02 | 整体运行 | 正在处理、运行中 | **处理中** | 仅表示任务尚在执行；当前动作另行说明 |
| CP-03 | 整体成功 | 已完成 · 耗时 | **已完成 · 8分5秒** | 只有任务成功终态；不是片段完成或没有新输出 |
| CP-04 | 整体失败 | 处理失败、失败 | **处理失败** | 附具体原因；只有可重试时才提供相应入口 |
| CP-05 | 已确认暂停 | 已暂停 | **已暂停** | 执行器确认到达安全点后使用；只暂停后续调度时用 CP-42 |
| CP-06 | 停止正在生效 | 正在停止、停止中 | **正在停止…** | 停止请求发出至执行器确认结束；不可提前写“已停止” |
| CP-07 | 用户停止后终态 | 已停止、已取消 | **已停止** | 对话域包括后台任务控制统一“停止”；不修改内部 cancelled 枚举 |
| CP-08 | 缺少可靠终态 | 执行状态待确认 | **任务状态暂无法确认** | 仅有可信任务结束时间但缺终态时：“任务已结束，结果状态未记录”；活动结束时间不构成依据 |
| CP-09 | 批量阅读控制 | 展开全部过程／收起全部过程 | **保留现有文案** | 只控制第一层，不清空第二层阅读选择 |
| CP-10 | 历史边界未知 | 过程记录（未提供推进边界） | **过程记录** | 说明：“此记录未包含分段信息，按原始顺序展示。”不虚构段数 |
| CP-11 | 记录数量 | N 条记录 | **保留现有文案** | 记录数不改写成步骤数或执行轮数 |

### 5.2 初始准备、等待与生成

| 编号 | 可确认状态 | 当前文案或风险 | 设计文案 |
| --- | --- | --- | --- |
| CP-12 | 提交用户消息 | 发送中 | **正在发送…**；输入区紧凑状态可用“发送中” |
| CP-13 | 准备材料和调用参数 | 正在准备请求；初始段“处理请求” | 当前动作 **正在准备…**；初始段 **准备任务** |
| CP-14 | 读取指定文件 | 正在读取文档结构等 | **正在读取《{文件名}》…**；若只解析结构，则 **正在解析文档结构…** |
| CP-15 | 调用已经发出，尚无返回 | 思考中 | **等待模型响应…**；当前需细化发起请求事件后才能精确使用 |
| CP-16 | 回答内容正在产生 | 生成中；空消息可能回退为准备 | **正在生成回答…**；段标题“生成回答” |
| CP-17 | 生成修改提案而非直接回答 | 同为 streaming | **正在生成修改建议…**，由已确认任务类型决定 |
| CP-18 | 补充已有文档概况 | 正在补充文档画像 | **正在补充文档概况…**；详情说明是否包含正文 |

初始段统一为“准备任务”。准备本身是执行的一部分；有更具体动作时显示真实动作，没有材料准备事件时直接使用“处理中”，不补造准备记录。

不能仅凭内部枚举 `thinking` 一律显示“正在理解你的请求”或“深度思考”。若没有更细事件，使用中性的“处理中”，不描述无法确认的模型行为。

### 5.3 长文本分析与动作记录

| 编号 | 实际动作 | 段标题 | 当前动作或完成事件 |
| --- | --- | --- | --- |
| CP-19 | 读取并分块 | 阅读与分段 | “正在将文本分成可分析的片段…”；“已划分为 {N} 个文本片段” |
| CP-20 | map 分析 | 分析文本片段 | “正在分析第 {i}/{N} 个文本片段…”；“第 {i} 个文本片段分析完成” |
| CP-21 | 确有章节归组 | 汇总章节分析 | “正在汇总第 {i}/{N} 章的分析结果…” |
| CP-22 | 确有分卷归组 | 汇总分卷分析 | “正在汇总第 {i}/{N} 卷的分析结果…” |
| CP-23 | 多层摘要归并 | 汇总分析结果 | “正在进行第 {k} 轮汇总，处理第 {i}/{N} 批…”；该轮指汇总层，不指 Agent 执行轮次 |
| CP-24 | synthesis 综合 | 综合分析 | “正在综合分析结果…”；任务范围确定为全书时才使用“全书” |
| CP-25 | 引用检验 | 核对引用 | “正在核对引用与原文…”；“已核对 {N} 条引用，{V} 条与原文匹配” |
| CP-26 | 使用有效已有结果 | 沿用当前真实段 | “已复用此片段的分析结果”；完整输出复用时“已复用本次任务可用的分析结果” |
| CP-27 | 阶段明确结束 | 沿用段标题 | “文本片段分析完成”等明确阶段完成事件；不能用任一活动完成替代 |
| CP-28 | 可查阅阶段文件 | 查看产物清单 | **查看分析文件**；详情保留真实文件名和只读属性，须与实际打开内容一致 |

进度只表示对应对象：片段数、章节数、批次数不能互换。只有当前位置而无可靠总数时，显示“正在分析第 {i} 个文本片段…”，不制造百分比或预计剩余时间。处理了全部片段也不代表综合、校验和保存已全部完成。

“引用与原文匹配”不等于文学解释、推论或所有事实均已证实。复用结果也不表述为刚刚重新阅读全文。实现层的 Rust、Worker、Map、manifest、缓存键和 token 预算可在详情或日志保留；用户主文案优先回答动作和范围。

### 5.4 继续、失败与历史查阅

| 编号 | 场景 | 设计文案 | 限制 |
| --- | --- | --- | --- |
| CP-29 | 用户发起继续 | 按钮“继续处理”；处理中间态“正在继续…”；确认后“已继续处理” | 三者不能同时当成已恢复的证据 |
| CP-30 | 自动重试等待 | “本次调用未完成，将进行第 {n} 次尝试” | 只有已确定的重试策略才显示；等待秒数须有实际依据 |
| CP-31 | 自动重试开始 | “开始第 {n} 次尝试” | 说明是该次调用的尝试次数，不是整个任务从头执行次数 |
| CP-32 | 用户选择步骤重跑 | “从「{步骤名}」重新执行” | 保留旧失败记录；明确可能重跑所选步骤及其后续步骤 |
| CP-33 | 历史记录有缺失 | “部分过程记录缺失，当前仅展示已保留的记录。” | 缺失不等于任务失败；不由最终答案补造历史 |
| CP-34 | 历史读取失败 | “暂时无法读取过程记录。” | 与记录不存在区分；只有实现读取重试后才提供“重试读取” |
| CP-35 | 来源发生变化 | “原文已变化，无法沿用此前进度。请重新发起分析。” | 仅用于确已验证失配的恢复失败；不承诺从旧进度继续 |
| CP-36 | 结果待用户处理 | “修改建议已生成，待审核”／“已整理记忆候选，待确认” | 与回答生成状态分别表达；不虚报已应用或已保存 |
| CP-37 | 真实计划可供查看 | “处理计划” | 计划条目与已发生记录分开；当前无通用计划对象时不自动展示 |
| CP-38 | 必要信息阻塞任务 | “需要你补充{具体信息}” | 给出可回答的问题；仅非阻塞追问时不将整体状态改为等待 |
| CP-39 | 已确认后台持续执行 | “正在后台处理” | 必须对应持续运行的任务与会话；不承诺退出应用后继续 |
| CP-40 | 区分控制对象 | “继续处理”／“从此步骤重新执行”／“还原文稿” | 每个入口只在已有对应能力时提供；历史查阅不能被称为重新执行 |

### 5.5 控制请求、阻塞、文件与异常补充

| 编号 | 场景 | 设计文案 | 触发与操作 |
| --- | --- | --- | --- |
| CP-41 | 暂停请求处理中 | 正在暂停… | 禁用本任务重复暂停/继续；等待明确回执 |
| CP-42 | 仅暂停后续调度 | 已暂停后续步骤；“当前操作结束后将停在下一步之前。” | 当前实现仅设置暂停标志时使用；不能宣称在途调用已经停止 |
| CP-43 | 暂停、继续或停止失败 | “{操作名}未成功：{可读原因}” | 保留最近已确认状态，重新查询；查询也失败用 CP-08，不假装已恢复执行 |
| CP-44 | 等待必要答复 | 等待答复；“需要你补充{具体信息}” | 只在运行被真实阻塞时出现；可编辑的答复入口与问题放在折叠外 |
| CP-45 | 等待运行授权 | 等待确认；“确认后将{动作与范围}” | 使用已有审批组件及允许/拒绝语义；结果待审用 CP-36 |
| CP-46 | 执行器已接收、尚未开始 | 等待开始 | 只有 planned/已受理的事实；未发送草稿不创建此状态，不虚报排队名次 |
| CP-47 | 已知没有过程记录 | 暂无可展示的过程记录 | 历史列表成功读取且为空；若执行还在进行，状态栏继续显示运行状态 |
| CP-48 | 有新页记录 | 有新记录 · 查看最新记录 | 转到最新页和活动位置，保留折叠选择 |
| CP-49 | 停止确认 | “停止此任务？已生成的内容和已保存的分析文件会保留。” | 长文本后台任务沿用一次确认；按钮“暂不停止”/“停止任务”；同一长文本任务从任一入口停止都使用同一确认；普通流式停止不额外确认 |
| CP-50 | 步骤重新执行确认 | “从「{步骤名}」重新执行？此步骤及依赖它的后续步骤将重新处理，已有过程记录会保留。” | 按实际重跑范围显示；按钮“返回”/“重新执行”，不混用“继续处理” |
| CP-51 | 只读文件预览 | 分析文件（只读）；分析文件清单 | 复用已有预览；文件不存在：“该分析文件尚未生成或已失效。”；读取异常：“暂时无法读取分析文件。” |
| CP-52 | 停止/失败后保留成果 | 部分结果；“任务未完整完成，以下是已生成的内容。” | 仅在确有输出时显示；已停止但无结果不创建空结果卡片 |
| CP-53 | 历史持久化失败 | 过程记录保存失败，重新打开后可能不完整 | 保留内存中的过程与结果；不显示没有实现的保存重试按钮 |
| CP-54 | 文稿另行保存失败 | “未能保存《{文件名}》：{可读原因}” | 仍保持未保存标记，不把生成任务改成失败 |
| CP-55 | 长时间没有新事件 | “暂未收到新的进展，任务状态以执行器回报为准。” | 执行中距最近公开事件（无事件则距任务开始）满 30 秒时显示一次，附最近更新时间；新事件到达即撤下。没有心跳不能断言仍正常工作，UI 不自行判定超时失败 |
| CP-56 | 跨端能力不支持 | 此操作仅在桌面应用中可用 | 有历史数据但当前端无步骤重试/文件访问能力时说明原因，不提供无效按钮 |

占位符由结构化事实填入，缺值时删去对应片段，不显示 `undefined`、空括号或假总数。错误先给可读原因，原始诊断在活动详情保留；不把错误堆栈直接作为主要文案。按钮中的“取消”仅用于放弃尚未提交的普通对话框操作，运行任务的动作统一为“停止”。CP-49 的“暂不停止”只关闭确认框，不改变任务状态；真正恢复按钮固定为“继续处理”。

## 6. 语气、重复呈现与历史时态

系统固定提示推荐用客观短语：“正在读取…”“已完成…”；助手公开说明可以使用自然叙述：“文件较长，我会分段分析，再汇总结果。”后者只有在执行方案已经确定时才适用，不要由 UI 擅自补写助手承诺。

| 场景 | 规则 | 示例 |
| --- | --- | --- |
| 同一事件同时出现在当前标题与说明 | 可以只显示一次，或标题用阶段名、说明用具体动作；不改动历史数量 | “分析文本片段”＋“正在分析第 3/15 个文本片段…” |
| 两次真实读取使用相同名称 | 两条记录均保留，通过所属段、时间或尝试编号识别 | 两条“读取《文稿.txt》”可独立展开 |
| 当前进行中的动作 | 使用进行时 | “正在读取《文稿.txt》…” |
| 当时记录的是开始 | 保留开始事实；说明当时状态，不事后改写成成功 | “开始读取《文稿.txt》”／“当时状态：执行中” |
| 明确完成事件 | 使用完成时 | “《文稿.txt》读取完成” |
| 仅有 `completedAt` | 不据此宣称动作成功 | 当前本地记录的该字段也可能仅表示下一状态到达或活动区间结束 |
| 正在等待 | 使用省略号，模板统一为中文字符“…” | “等待模型响应…” |
| 已结束或需操作 | 不以省略号和呼吸动画制造仍在执行的感觉 | “处理失败”“待确认” |

建立同一份状态到文案的映射，供消息区和输入区调用。紧凑状态“生成中”和完整提示“正在生成回答…”可以并存，但必须指向同一事实。历史事件的原始文字和数据保留；新增展示文案不覆盖已存记录，也不靠解析旧字符串猜测状态。

## 7. 状态依据与实现依赖

以下是实施必须遵守的事实约束。需要新事件的状态先补齐依据，再启用精确文案；本次文档交付不修改 Runtime。

| 需要表达的事实 | 当前依据 | 仍需补齐或明确的部分 |
| --- | --- | --- |
| 正在生成 | 首个 chunk 已触发 `streaming` | 展示组件需要按状态兜底；任务类型决定“回答”还是“修改建议” |
| 等待模型响应 | 当前 `thinking` 同时覆盖多个阶段 | 明确请求发起边界；准备和等待分开，不新增假的思考事件 |
| 一个推进段确已结束 | 有部分阶段完成事件，也有许多单项完成事件 | 显式区分活动结束与段结束；视图所需字段见第 7.2 节，实现可复用已有生命周期事件，不要求新增通用协议 |
| 推进段耗时 | 有段开始时间；当前常取最后记录时间 | 结束时间须来自明确段结束事实；缺少依据时省略完成耗时，不把最后活动时间当作段结束 |
| 暂停已生效 | 当前原生端设置暂停标志并发布 paused | 当前只设置暂停标志时使用 CP-42；有安全点确认后才用 CP-05。收到暂停标志不能伪造在途调用已停止 |
| 停止已完成 | 有停止请求与执行终态 | 请求动作、等待退出和终态分开；不能点击后立即显示终态 |
| 正在恢复或重试 | 原生恢复和调用重试有相应行为与记录 | 使用结构化原因、尝试范围与次数；不同执行路径不能仅靠标签推断 |
| 历史读取失败 | 有读取错误与缺口提示 | 不覆盖已知任务终态；“读取失败”不是“任务失败” |
| 有步骤等待用户确认 | 修改提案、记忆候选已有专门区域 | 仅在执行本身被阻塞时使用整体“等待确认”；候选待审不必阻塞已完成回答 |
| 计划与真实执行不同 | 当前有确定性任务策略与部分公开说明 | 尚无覆盖所有任务的用户计划清单；需明确计划对象、实际执行事件与版本关系，不预先填满步骤 |
| 后台运行与前台停止不同 | 已有部分后台 Worker 能力与任务归属 | 按具体链路验证存活范围；普通流式回答不能套用后台任务承诺 |

当前状态提示优先描述正在执行的事实；已经确认的任务终态不被某个较早活动的失败覆盖。恢复、重试过程中发生的新状态应保留在其对应时间位置，历史终态不因 UI 文案升级被改写。

### 7.1 状态、按钮与事实优先级

生命周期、当前动作和控制请求是三个独立维度。例如任务仍处于执行中，同时有暂停请求在等待回执；某次工具调用失败但已安排重试，不等于任务失败。不得只读“最后一条活动”确定整个任务的状态。

| 已确认事实 | 状态行 | 可用操作 | 不可使用的推断 |
| --- | --- | --- | --- |
| 已受理尚未执行 | 等待开始 | 仅有取消受理能力时允许停止 | 草稿已输入≠任务已排队 |
| 正在执行 | 处理中 | 停止；执行器支持时显示暂停 | 没有新 token≠卡死 |
| 请求已发出且未收到响应 | 处理中；当前“等待模型响应…” | 同执行中 | `thinking` 字段本身不证明发出了请求 |
| 正在生成响应 | 处理中；当前“正在生成回答/修改建议…” | 停止 | 首个 chunk 后不再兜底为准备 |
| 正在申请暂停/停止/继续 | 正在暂停… / 正在停止… / 正在继续… | 锁定该任务互斥命令；仍可阅读/复制 | 请求返回之前不显示目标状态 |
| 后续步骤暂停、在途操作未确认结束 | 已暂停后续步骤 | 继续处理、停止任务 | 不显示“所有执行已暂停” |
| 安全点确认暂停 | 已暂停 | 继续处理、停止任务 | 不把查看历史当继续 |
| 被必要答复或授权阻塞 | 等待答复 / 等待确认 | 对应答复/审批、可用时停止 | 不继续播放普通执行动画 |
| 已安排自动重试 | 处理中；显示 CP-30/31 | 停止；暂停依能力 | 调用失败不覆盖任务生命周期 |
| 成功终态 | 已完成 | 复制、结果审核/保存；后续需求正常发送 | 未保存文稿≠任务仍生成 |
| 失败终态 | 处理失败 | 可重试时选择步骤并重新执行；否则给重新发起指引 | 不自动重发失败任务 |
| 用户停止终态 | 已停止 | 阅读/复制已有结果、正常发起新请求 | 本阶段不为 cancelled 任务承诺断点继续 |
| 状态读取失败或终态缺失 | 任务状态暂无法确认 | 阅读已有结果；控制动作须重新校验任务状态 | 不凭无活动或结束时间猜成功 |

同一任务的权威生命周期结果优先于历史活动；较新的续接事实可将其进入新的执行尝试，旧终态作为历史保留。控制请求待回执时只覆盖当前显示提示，不改写已确认状态；若任务先于控制请求结束，以真实终态显示并解除按钮锁。任务状态查询失败与历史记录读取失败分别提示，后者不抹掉已确认终态。

### 7.2 展示所需的最小事实

下表是前后端实现约定，不是用户界面字段，也不是要求另起 Runtime 工程。

| 对象 | 展示所需事实 | 缺失时降级 |
| --- | --- | --- |
| 任务 | 稳定任务/请求标识、会话/工作区归属、生命周期与来源、是否支持暂停/停止/步骤重试、起止时间 | 不跨任务借状态；禁用无法确定的控制；时间未知则省略历时 |
| 控制请求 | 操作类型、请求标识、请求中/成功/失败；暂停范围与安全点回执 | 显示请求中，失败重查；仅设置调度暂停用 CP-42 |
| 推进段 | 稳定 ID、开始时间、可读标签；可选的原因与明确结束事实 | 标签缺失用“处理过程”/“继续处理”；无边界用未分段记录，结束未知不打完成勾 |
| 活动 | 稳定事件身份、顺序、时间、具体动作与对象、当时状态、真实范围/进度、原始公开消息 | 老记录保留原消息；不从文字相似度合并事件，不把 interval 结束当成功 |
| 响应与产物 | 真实交付内容、所属任务/段/事件、交付时序、文件是否存在、审核/保存结果 | 无对象不显示入口；部分响应标部分结果，不创建虚构报告小节 |
| 历史 | 读取成功/失败、已加载数、总数是否可靠、已知缺口、保存结果 | 缺口提示不改变任务结果；未拿到总数只显示已加载数 |

统一产出一个共享的界面状态映射，由消息区和控制行消费；不在每个组件分别猜测状态。历史原始消息保持不变，有结构化类型的新记录使用统一文案，原文可在同一活动详情查阅。未知类型使用原有可读消息或“处理记录”，不要默认成“准备请求”。

总历时从真实任务开始至终态的墙钟时间计算，包含等待和暂停；运行中需要显示时用当前时间，暂停不暗示计时就是纯执行用时。完成示例“8分5秒”仅在时间可信时出现，可访问说明写“总历时，包含等待和暂停”。未知结束时间不借最后一条活动时间补齐；段耗时遵守同样规则。进度按片段/章节/批次分别计数，不显示全任务虚假百分比或无依据的预计剩余时间。

### 8.2 小说长文本分析

```text

展开全部过程  收起全部过程

▸ 阅读与分段
▾ 分析文本片段
    ▸ 第 1 个文本片段分析完成
    ▸ 第 2 个文本片段分析完成
    ▾ 开始分析第 3 个文本片段
        来源：《文稿.txt》及实际原文位置
        当时已完成：2/15 个文本片段

后续实际发生时：
▸ 汇总分析结果
▸ 综合分析
▸ 核对引用

处理过程 · 已完成 · 8分5秒
这里显示实际完整返回的分析正文。
```

如果 Runtime 期间确已交付某段公开响应，放在对应过程之后，并在全部收起时保持可见；当前长文本流程若只在结束时返回完整报告，就仅展示该完整报告。不能根据任何竞品的交付样例预先放置“人物分析”“主题评价”等中间结果。

### 8.3 暂停、继续与失败重试

```text
用户请求暂停：正在暂停…                  需相应动作状态支持
仅确认调度暂停：已暂停后续步骤             当前操作可能仍在结束中
安全点确认暂停：已暂停                   需真实回执
操作：继续处理  停止任务

确认继续后：处理中
▸ 分析文本片段                           暂停前的段保留
▾ 继续分析文本片段                       实际恢复后的新段
    ▸ 已继续处理

发生调用失败：本次调用未完成，将进行第 2 次尝试
真正重试时：
▾ 重新分析文本片段
    ▸ 开始第 2 次尝试
```

自动重试未耗尽时，某次调用失败不必让整个任务成为失败终态。重试耗尽且任务终止后显示“处理失败”，并按能力提供“从此步骤重新执行”或“重新发起任务”。

### 8.4 回答完成但修改或记忆待处理

```text
处理过程 · 已完成 · 35秒
实际回答或修改说明。

修改建议已生成，待审核       查看修改建议
已整理 3 条记忆候选，待确认  查看候选
```

两个待处理入口只在确有相应对象时出现。“已完成”指本次生成任务结束；正式修改、保存或确认记忆的结果按真实后续操作反馈。
