# UI 测试验收脚本编写工作计划

- 计划基线：当前版本 `0.1.0`
- 计划日期：2026-09-22
- 设计规范：[UI_ACCEPTANCE_SCRIPT_SPEC.md](./UI_ACCEPTANCE_SCRIPT_SPEC.md)

> 说明：跨功能域的排序主表维护在 [`UI_ACCEPTANCE_PLAN.md`](./UI_ACCEPTANCE_PLAN.md) 第 3 节；本文件只维护脚本建设、执行和归档计划。脚本矩阵沿用主表的 W0-W4 验收波次，不另行定义一套可能冲突的优先级。

## 1. 工作目标

为每个高影响功能域建立一套可重复的三层证据：自动化测试证明代码合同，本地环境脚本证明 macOS/Windows + Ollama 或兼容服务的真实链路，人工 UI 记录证明入口、状态、键盘和视觉行为。脚本编写完成不等于功能验收完成；必须等测试人员上传脚本输出和人工观察后，验收报告才能给出平台层结论。

## 4. 模型设置专项的首轮执行计划

1. 先完成 W0-A 的壳层、入口和响应式基线；该阶段可以不配置模型，但报告结论限定为结构/UI 子范围。
2. W0-B 可并行执行基础文件与编辑器链路；明确不覆盖 AI 改稿和模型辅助操作。
3. 测试人员启动目标版本 Vinkey，在设置页确认要验收的 profile、模型和 connection。
4. 执行 `--list-profiles`，确认 SQLite 中带“当前”标记的 profile；不确认前不得直接跑全量评测。
5. 使用固定 `--profile-id` 执行真实 Ollama 评测，保存人类输出、`--json` 结果和诊断日志。需要兼容服务 API Key 时只通过临时环境变量传入。
6. 按回填模板逐项操作设置页：打开/返回、保存并检查、刷新目录、切换活动模型、删除服务/密钥、低配或未知硬件入口。
7. W1 通过后再执行 W2 对话；W3 补充上下文/分析和 AI 改稿；W4 执行真实长任务与日志闭环。
8. 记录 OS 版本、架构、Vinkey 版本/Git SHA、Node/Rust/Ollama 版本、模型标签、数据库位置（脱敏）和命令退出码。
9. 上传 `result.json`、日志、人工观察表和截图/录屏索引；在报告中只保留摘要和 SHA-256。
10. 根据规则更新结论：所有必要层级通过为“通过”；仅代码层或缺平台证据为“条件通过”；业务断言失败为“不通过”；无法执行为“阻断”。

## 5. 每个新脚本的编写任务单

| 任务 | 产出 | 必检项 |
| --- | --- | --- |
| 用例建模 | 稳定的 `caseId`、目标、前置条件、预期和清理动作 | 成功、失败、空态、禁用、恢复至少各一项 |
| 核心实现 | 一个 TypeScript 核心入口 | 只读配置、超时、取消、日志和错误归因 |
| 平台包装 | `.sh`、`.ps1` 和 npm 命令 | 从仓库外目录执行、中文路径、退出码透传 |
| 输出实现 | 人类摘要、JSON、逐用例日志 | schemaVersion、环境、模型、计数、结论和脱敏 |
| 合同测试 | `tests/<domain>/*-cli.test.ts` | 参数、边界、失败注入、字段稳定性 |
| 手工说明 | 专项报告回填区和操作步骤 | 不把未填写占位符当作 PASS |
| 归档 | 结果目录和 `SHA256SUMS` | 原始证据可追溯，不提交密钥/正文 |

## 6. 完成定义与阻断处理

脚本只有同时满足以下条件才可标记“已有”：

- 核心实现、macOS/Linux 入口、Windows 入口和 npm 入口都存在。
- CLI 合同测试通过，并验证非零退出码不会被包装器吞掉。
- `--json` 结果可被报告模板引用，字段包含实际版本和环境信息。
- 至少有一次从仓库外目录的手工冒烟记录。
- 已定义真实服务不可用、超时、无 profile、非法输出和用户取消的归因。

环境库缺失、Ollama 未启动、没有目标模型或系统凭据不可用时，应产出 `BLOCKED` 结果和复现信息，不能修改脚本绕过检查。开发机 Linux 的 GTK/GLib 缺失只阻断 Rust/桌面层证据，不自动否定前端组件测试。

## 7. 复审节奏

- 每次 Vinkey 版本发布：重跑 P0 脚本并回填报告。
- P1 功能或模型准入规则变更：重跑受影响功能域及其依赖域。
- 本地模型、提示合同、输出 schema 或连接协议变更：重新执行 IntentRouter 和模型设置专项。
- 竞品证据或 UI 决策变更：先更新 `FEATURE_DECISIONS.md`，再更新受影响脚本用例和报告。
